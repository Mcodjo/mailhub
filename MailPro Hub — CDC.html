1Contexte & vision

Vision v2 : L'outil ne se contente plus de configurer une adresse mail pro — il devient la boîte mail elle-même. L'utilisateur envoie et reçoit ses mails directement dans l'interface, sans passer par Gmail.

La v1 du concept reposait sur une redirection Cloudflare vers Gmail. Cette approche reste valide pour les cas simples, mais elle présente une limite : l'utilisateur doit jongler entre deux interfaces (l'outil pour configurer, Gmail pour lire et répondre).

La v2 centralise tout : configuration, réception, rédaction et envoi se font dans un seul outil. Cloudflare reçoit les mails entrants et les pousse vers le backend de l'outil. L'envoi s'appuie sur Gmail SMTP via OAuth, ce qui garantit une excellente délivrabilité sans gérer de serveur mail.

2Concept de l'outil

MailPro Hub est un webmail SaaS léger où chaque utilisateur peut :

Configurer son domaine

Wizard rapide : domaine → Cloudflare → DNS → c'est prêt

Recevoir ses mails

Les mails envoyés à contact@domain.com arrivent dans l'interface de l'outil

Envoyer des mails

Rédiger depuis l'outil, envoi via Gmail SMTP — l'expéditeur affiché est l'adresse pro

Répondre aux conversations

Threads groupés, réponse directe — le destinataire voit l'adresse pro à tout moment

Multi-adresses

contact@, info@, support@ — plusieurs alias sur le même domaine

Zéro serveur mail

Pas de Postfix, pas d'IP à gérer — Cloudflare pour recevoir, Gmail pour envoyer

Flux réception

1
Quelqu'un envoie un mail à contact@domain.com
2
Cloudflare Email Routing intercepte le mail (enregistrement MX)
3
Un Cloudflare Worker analyse le mail et fait un POST vers l'API du backend
4
Le backend enregistre le mail en base de données (expéditeur, objet, corps, pièces jointes)
5
L'utilisateur voit le mail dans son interface webmail en temps réel (WebSocket ou polling)

Flux envoi

1
L'utilisateur rédige un mail dans l'interface de l'outil
2
Il clique Envoyer
3
Le backend appelle Gmail SMTP avec le token OAuth de l'utilisateur
4
Gmail expédie le mail — l'expéditeur affiché est contact@domain.com
5
Le mail est archivé dans la boîte Envoyés de l'outil

⚠️ Contrainte Gmail SMTP

Gmail SMTP limite à 500 mails/jour (compte gratuit) et 2 000/jour (Google Workspace). Pour les utilisateurs à fort volume, prévoir une option de bascule vers Brevo ou Mailgun. L'utilisateur doit avoir autorisé l'outil via OAuth Google — les credentials restent stockés côté serveur, chiffrés.

6Modules détaillés

Module 1 — Authentification & comptes

  • Inscription par email + mot de passe (hash bcrypt)
  • Connexion Google OAuth optionnelle
  • Profil utilisateur : nom, photo, domaines configurés, token Gmail
  • Sessions sécurisées (JWT ou sessions serveur)
  • Réinitialisation de mot de passe par email

Module 2 — Wizard de configuration domaine

Étape 1 : Saisie du domaine + préfixe(s) d'adresse (ex. contact)
Étape 2 : Connexion à l'API Cloudflare (token API) → activation Email Routing → déploiement du Worker
Étape 3 : Affichage du tableau DNS complet (MX Cloudflare, SPF, DKIM selon SMTP choisi, DMARC)
Étape 4 : Polling DNS — vérification propagation en temps réel (MX, SPF, DKIM, DMARC)
Étape 5 : Test d'envoi + test de réception dans l'outil → validation finale

Module 3 — Connexion Gmail OAuth (envoi SMTP)

Flux OAuth 2.0 :

  • L'utilisateur clique "Connecter mon compte Gmail"
  • Redirection vers Google OAuth → consentement pour le scope gmail.send
  • Le backend reçoit le access_token + refresh_token et les stocke chiffrés (AES-256) en base
  • Pour chaque envoi, le backend renouvelle le token si expiré et appelle Gmail SMTP via Nodemailer (ou PHPMailer) avec From: contact@domain.com
  • L'utilisateur peut déconnecter son compte Gmail depuis son profil
Le scope minimal requis est https://mail.google.com/ ou gmail.send. Ne jamais demander d'accès en lecture à Gmail — uniquement l'envoi.

Module 4 — Réception via Cloudflare Worker

Le Worker Cloudflare est déployé automatiquement lors de la configuration du domaine. Il :

  • Reçoit chaque mail entrant via l'événement email de Cloudflare Email Routing
  • Extrait les données : expéditeur, destinataire, objet, corps (texte + HTML), en-têtes
  • Fait un POST signé (HMAC secret) vers l'endpoint /api/inbound-mail du backend
  • Le backend vérifie la signature, identifie l'adresse destinataire, associe au bon utilisateur et enregistre le mail en base
  • Une notification temps réel est déclenchée (WebSocket ou Server-Sent Events)

Module 5 — Interface webmail

Interface à trois colonnes (sidebar / liste mails / lecture-rédaction) :

ZoneContenu
SidebarBoîtes (Réception, Envoyés, Brouillons), domaines configurés, bouton Nouveau mail
Liste des mailsExpéditeur, objet, aperçu du corps, date, badge non-lu, indicateur pièce jointe

RédactionModal ou panneau : De (adresse pro), À, CC, Objet, éditeur riche (gras, liste, lien), Envoyer

9Phases de développement

Phase 1

Fondations — Auth + Configuration domaine

4 à 6 jours
  • Authentification (inscription, connexion, JWT)
  • Wizard de configuration domaine (Cloudflare API, DNS, vérification propagation)
  • Déploiement automatique du Cloudflare Worker
  • Endpoint backend /api/inbound-mail + signature HMAC
Phase 2

Réception & boîte de réception

3 à 4 jours
  • Stockage des mails entrants en base
  • Interface boîte de réception (liste + lecture)
  • Notifications temps réel (WebSocket ou polling)
  • Tri, filtre, marquage lu/non-lu
Phase 3

Envoi via Gmail OAuth

3 à 4 jours
  • Flux OAuth 2.0 Google (scope gmail.send)
  • Stockage sécurisé des tokens (AES-256)
  • Éditeur de rédaction (TipTap)
  • Envoi via Gmail SMTP + archivage dans Envoyés
  • Réponse dans un thread existant
Phase 4

Polish & code d'intégration

2 à 3 jours
  • Génération des snippets Laravel/Node.js/WordPress
  • Score délivrabilité (SPF/DKIM/DMARC alignés)
  • Test d'envoi + test de réception intégrés au wizard
  • Interface responsive mobile
Phase 5 (V2)

Multi-alias, pièces jointes & équipe

5 à 7 jours
  • Multi-alias par domaine avec boîtes séparées
  • Pièces jointes (upload + stockage R2/S3)
  • Recherche full-text
  • Multi-utilisateurs par domaine
  • SMTP alternatif (Brevo) pour gros volumes

Envoi depuis l'outilUn mail rédigé dans l'outil arrive dans la boîte du destinataire avec contact@domain.com comme expéditeur affiché

OAuth sécuriséLe token Gmail n'est jamais exposé côté client ni dans les logs
